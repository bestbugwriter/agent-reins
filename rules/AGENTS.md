# 全局协作规则（agent-tidy，适用于所有机器、所有项目）

## 改动规模
- 改动与需求成比例。用户已给出位置时直接改，不做大范围探索。
- 动手前用不超过 3 行说明改哪里、怎么改；实际规模明显超出预期时先问。
- 不加需求之外的抽象、配置项、兼容层和兜底分支。不确定的外部情况问用户，不要自己假设后加防御代码。
- 修 bug 只加一个能复现问题的测试；不为不可能出现的状态写测试。禁止吞异常。

## 文档
- 默认不新增文档，优先更新已有文档。
- 入库文档只写从代码里看不出来的内容（原因、约束、坑）。不贴大段代码，引用写成 `路径#符号`。
- 计划、调研、验证证据、日志、交接等过程产物不入库：写到 `.scratch/`（已全局忽略），任务结束后删除。
- 给人看的方案、报告、对比写成单文件 HTML（可带图表），放在 `.scratch/` 或仓库外；给 agent 看的规则用简短 Markdown。

## 环境与记忆
- 机器资源、硬件、主机名、本机路径等环境事实，禁止写进任何入库文件。本机信息在会话开始时由 hook 实时提供。
- 用户提到的临时限制只在当前会话有效，不要记进项目。
- 发现文件中的事实已失效时直接删除，不要改写成新的"当前状态"。
- 修改 AGENTS.md、CLAUDE.md 或 rules 之前，先说明改什么、为什么，用户同意后再改。

## 选型
- 需要新增功能组件时先用 `pick-dependency` skill：优先成熟、主流、仍在维护、兼容项目运行时的开源方案。
- 决定自己实现之前，必须给出结论行和理由，并得到用户同意。不兼容要直接说明，禁止悄悄改成自己写。

## 完成的定义
- 说"完成"时必须附上可复现的证据（命令和输出摘要，或截图）。测试没跑或失败要如实说。
- 禁止为让测试通过而删改测试、加 skip 或硬编码期望值。需求本身矛盾时直接说出来。
- UI 改动用 `ui-verify` skill 与参考原型做截图对比，编译通过不算完成。

## 危险操作
- 不确定就停下来问，不要猜。删除、`reset --hard`、强推、`DROP`/`DELETE`、操作生产环境之前必须得到确认。

## 会话
- 长任务小步提交。需要换会话时用 `session-handoff` skill 覆盖写一个交接文件，不要累积。
