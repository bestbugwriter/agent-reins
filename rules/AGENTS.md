# 全局协作规则

优先级：用户当次的明确指令 > 本规则 > 项目流程（Comet、OpenSpec、Superpowers 等）。项目流程与本规则冲突时（尤其是文档数量、过程记录），按本规则执行；项目里的构建命令、目录约定等事实性规定照常遵守。

## 改动范围
- 用户已给出位置时直接改，再查改动点的引用；不做与任务无关的大范围探索。
- 动手前用不超过 3 行说明改哪里、怎么改；实际范围明显超出时先问。
- 不加需求之外的抽象、配置项、兼容层和兜底分支。不确定的外部情况问用户，不要自己假设后加防御代码。禁止吞异常。
- 未经要求不改 CI、部署脚本、构建配置、锁文件和密钥；不用 `git add -A`、`--no-verify`；不提交凭证。

## 一致性（同一次改动内闭环）
- 改了行为、接口、配置项或数据结构时，用 `change-impact` skill 找出受影响的调用点、测试、文档、注释和配置示例，并在同一次改动中更新，不留到以后。
- 测试按行为变化增删改：新行为加用例，变了的行为改断言，删掉的行为删对应用例并说明原因。修 bug 加一个能复现问题的用例。
- 过期的文档和注释视为 bug：在本次改动中更新或删除。注释只写"为什么"，不复述代码，不写会过期的数字、行号或"临时"说明。
- 文档与代码矛盾时以代码为准修正文档；怀疑代码才是错的一方时，先问用户。
- 完成时说明：更新了哪些测试、文档、注释；检查过但无需改动的有哪些。

## 文档
- 默认不新增文档，优先更新已有文档。项目流程要求的文档合并到最少的文件里，只写决策和约束，不写过程。
- 入库文档只写从代码里看不出来的内容（原因、约束、坑）。不贴大段代码，引用写成 `路径#符号`。
- 过程产物（计划、调研、验证证据、日志）写到 `.scratch/`，任务结束后删除。
- 给人看的方案、报告写成单文件 HTML，放在 `.scratch/reports/`，任务结束不删，并告诉用户路径。

## 环境与记忆
- 需要判断机器能否承受重负载时，当场用命令检测（如 `nproc`、`sysctl hw.memsize`、`free -g`），不从项目文件读取，也不写入项目文件。
- 用户提到的临时限制只在当前会话有效。发现文件里的事实已失效时直接删除，不要改写成新的"当前状态"。
- 修改 AGENTS.md、CLAUDE.md 或 rules 之前，先说明改什么、为什么，用户同意后再改。

## 选型
- 新增功能组件前，先查仓库里是否已有实现，再用 `pick-dependency` skill 找成熟、仍在维护、兼容当前运行时的开源方案。
- 决定自己实现之前必须给出理由并得到用户同意。不兼容要直接说明，禁止悄悄改成自己写。

## 完成的定义
- 说"完成"时附上可复现的证据（命令和输出摘要，或截图）。测试没跑或失败要如实说。
- 禁止为让测试通过而删改测试、加 skip 或硬编码期望值。需求本身矛盾时直接说出来。
- UI 改动用 `ui-verify` skill 与参考原型做截图对比。

## 危险操作与会话
- 删除、`reset --hard`、强推、`DROP`/`DELETE`、操作生产环境之前必须得到确认。
- 换会话时，项目有自己的恢复机制就用它；没有就用 `session-handoff` skill 覆盖写单个交接文件。
